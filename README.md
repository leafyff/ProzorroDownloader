# Prozorro Downloader

Настільна програма (Windows, PySide6) для збору даних публічних закупівель із
відкритих API Prozorro за заданими ознаками: період, клас ДК021 (CPV), ЄДРПОУ
конкурентів, замовник, статус, тип процедури.

На виході — **одна таблиця Excel** із сирими даними, придатними для власного
аналізу, і за потреби **тека з документами** закупівель. Ту саму таблицю
програма вміє розібрати сама: сторінка «Аналітика» будує з неї звіт по ринку —
очищення даних, рейтинги, портрети конкурентів, торгові марки й порівняння з
вашими ТОВ.

---

## Запуск

```bash
run.bat
```

Якщо середовище ще не створене:

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
```

`run.bat` стартує вікно без консолі. Якщо програма не відкривається або зникає
без пояснень — `run_console.bat`: там видно текст помилки.

> Обидва `.bat` навмисно містять лише латиницю. Кирилиця в них ламає `cmd.exe`:
> після `chcp` він губить позицію у файлі й виконує уривки рядків як команди.
> Це перевіряється тестом, щоб не повернулося.

## Дві кнопки — два режими

Внизу сторінки «Пошук і завантаження»:

| Кнопка | Що робить | На виході |
|---|---|---|
| **Порахувати** | лише пошук: скільки закупівель у фільтрі | нічого не зберігає |
| **Зібрати дані** (синя) | картки закупівель + картки товарів е-каталогу | таблиця Excel у `downloads` |
| **Зібрати файли** | те саме плюс документи закупівель | таблиця Excel + теки з файлами |
| **Зупинити** | перериває роботу; зібране лишається | — |

Хто купив, у кого, за яку суму, в якій галузі, хто ще подавався — усе це поля
картки закупівлі, а не вміст файлів. Тому «Зібрати дані» працює швидко: сотня
закупівель — близько хвилини.

«Зібрати файли» коштує на два порядки більше: сервер документів віддає близько
30–40 КБ/с на потік, тож гігабайт документації — приблизно година.

Порядок не обов'язково такий. Можна швидко зібрати дані, подивитися в
«Результатах», що знайшлося, і лише потім довантажити файли для тих самих
закупівель — кнопкою **«Завантажити відсутні»** на сторінці «Файли». Пошук
наново не запускається.

Налаштування під файли (розділи документів, підписи КЕП, типи файлів) живуть
у картці «Що збирати» в лівій колонці. На збір даних вони не впливають.

## Таблиця з даними

Створюється **автоматично** після кожного збору:

```
downloads\prozorro-дані-2026-08-17-2002.xlsx
```

Відмітка часу в назві, тому попередні файли не перетираються.

Жодних підсумків і рейтингів — лише сирі рядки, щоб рахувати у зведених
таблицях як потрібно. Порожні сутності аркушів не створюють.

| Аркуш | Що містить |
|---|---|
| Зміст | перелік аркушів із кількістю рядків і поясненням |
| Закупівлі | одна закупівля — один рядок: предмет, коди, замовник, суми, дати, посилання |
| Лоти | лоти закупівель, якщо предмет поділено |
| Номенклатура | позиції: товар, код ДК021, кількість, ціна за одиницю — основа аналізу товару й ТМ |
| Пропозиції | хто подавався і з якою сумою |
| Переможці | рішення про визначення переможця, а для відхилених — підстава, її категорія й пояснення замовника |
| Договори | ЄДРПОУ постачальника, сума, дата підписання |
| Відміни закупівель | закупівлі, які замовник відмінив: підстава з переліку та обґрунтування |
| Документи | реєстр усіх файлів: тип, чий, стан, шлях на диску, пряме посилання |
| Товари каталогу | бренд, модель, штрихкод, категорія, опис, квартилі ціни, фото, майданчик |
| Характеристики товарів | довгий формат: товар × характеристика × значення × одиниця |

Аркуші зв'язані через «Номер закупівлі» та ЄДРПОУ, товари — через штрихкод і бренд.

На сторінці «Результати» є ще дві кнопки: **«Вивантажити всі дані»** — та сама
таблиця, але коли потрібна поза розкладом; **«Зведення»** — окремий файл із
готовими підсумками (рейтинги постачальників, замовників, галузей, динаміка по
місяцях), якщо не хочеться рахувати самому.

## Аналітика

Сторінка **«Аналітика»** бере будь-яку книгу з теки завантажень і будує з неї
повний звіт по ринку. Мережа для цього не потрібна: усе рахується локально з
файлу, тож можна порівнювати періоди, брати вивантаження з іншої машини й
перераховувати звіт скільки завгодно разів.

**Аналітика читає тільки цей файл.** Ні бази, ні залишків попередніх зборів вона
не бачить: у жодному її модулі немає ані `sqlite`, ані `Database`, а сама
сторінка бази навіть не отримує. Звіт залежить рівно від обраної книги плюс двох
речей із налаштувань — ЄДРПОУ ваших ТОВ і список конкурентів — та вбудованих
довідників ДК021 і торгових марок. Це закріплено тестом, який проганяє аналіз із
підміненим `sqlite3.connect`: будь-яке звертання до бази впало б помилкою.

Звіт розкладено на десять вкладок, у кожній — показники, графіки й таблиці.
Графіки намальовані вручну на `QPainter` (кільцеві діаграми, стовпчики, смуги,
лінії, точкова хмара), бо QtCharts живе в Addons, яких у проєкті немає.

Книгу читає власний потоковий розбирач ([`xlsxfast.py`](app/core/xlsxfast.py)):
`openpyxl` на кожну клітинку з текстом створює об'єкт, і на двохсот тисячах
рядків це майже хвилина самої лише службової роботи. Тут XLSX розбирається
напряму — zip і потік подій без побудови дерева, з поверненням до `openpyxl`,
якщо книга виявиться незвичною.

### 1. Попередня обробка

Перш ніж рахувати суми, дані перевіряються на те, що робить підсумки
неправдивими:

* **структурний брак** — чужа валюта (перерахунок без курсу неможливий), нульові
  та від'ємні суми, дублікати договорів. Вилучається завжди;
* **суперечність із планом** — сума **всіх** договорів закупівлі утричі більша
  за її очікувану вартість або менша за 5% від неї. Саме всіх: у багатолотовій
  закупівлі кожен лот поодинці «мізерний» лише на вигляд;
* **статистичні викиди** — за модифікованим z-показником Іглвіча — Гоуліна
  (медіана й MAD замість середнього й стандартного відхилення) у логарифмі суми,
  **окремо по кожній галузі ДК021**. Але лише для тих угод, яким **нема з чим
  звіритися**: якщо сума договору збігається з очікуваною вартістю, це
  незалежне підтвердження, і статистиці там нічого перевіряти. Без цієї
  застороги поріг, порахований на ринку з медіаною 10 тис. грн, оголошує
  помилкою кожну закупівлю понад 18 млн — тобто саме ті договори, у яких
  лежить третина грошей;
* для **ціни за одиницю** статистика лише позначає, але нічого не вилучає:
  у вивантаженні ця ціна порахована як «вартість лоту ÷ кількість», тож
  звірити її нема з чим. Викинути «Скоби по 40 копійок» і «Модуль NetApp за
  37 млн» означало б прибрати з аналізу справжні товари разом з їхніми ТМ;
* схожі закупівлі одного дня — позначаються, але не вилучаються.

Окремо перелічені **угоди в іноземній валюті**: без курсу на дату договору
перевести їх у гривню чесно не можна, тож у підсумки вони не входять — але й
зникати мовчки не мають.

Видно все: таблиця повноти полів, перелік зауважень із причиною та дією,
розподіл сум і цін по галузях, гістограма угод і точкова хмара «ціна × кількість»
з підсвіченими викидами. Галочка «виключати статистичні викиди» вмикає й вимикає
третій пункт — структурний брак вилучається в будь-якому разі.

### 2. Ринок у цілому

Обсяг, кількість закупівель, постачальників і замовників, середня й медіанна
угода, HHI з висновком про концентрацію, CR3/CR5/CR10, коефіцієнт Джині,
скільки компаній дають 80% обороту, середня кількість учасників, частка
закупівель з одним учасником.

**Економія рахується там, де вона можлива** — у конкурентних процедурах. У
прямому договорі сума договору і є очікуваною вартістю, тож медіана по всій
вибірці завжди нуль і ховає всю картину. Окрема таблиця показує економію за
рівнем конкуренції: на реальних даних це 0% без конкуренції, 4,2% при двох
учасниках і 10,9% при трьох і більше.

**Обидва грошові ряди динаміки прив'язані до місяця оприлюднення закупівлі.**
Інакше вони описували б різні речі: договір, підписаний у серпні за червневою
закупівлею, дав би в червні «план без грошей», а в серпні — «гроші без плану».
Дата підпису лишається окремим рядом — вона відповідає на інше питання, коли
гроші реально розійшлися. Неповні крайні місяці позначені: вибірка
починається й закінчується посеред місяця. Динаміка по місяцях, топ
постачальників (наші ТОВ виділені кольором), структура за процедурами, галузями
ДК021 і регіонами, розподіл економії.

Гроші ринку — це підписані договори; там, де договору ще немає, береться чинне
рішення про переможця, щоб свіжі закупівлі не зникали з картини. Брати і те, і
те не можна — сума подвоїлася б.

### 3. Прогнозування

Вкладка продовжує місячну динаміку ринку на кілька місяців уперед — за
замовчуванням на три, горизонт задається на самій сторінці. Прогнозуються сума
угод, очікувана вартість, кількість закупівель і сума ваших ТОВ; окрема таблиця
дає прогноз по кожному помітному гравцю.

**Спершу — поправка на те, що останні місяці неповні.** Це головна пастка
всієї задачі. Договір з'являється не в день оприлюднення закупівлі, тож «сума
угод» свіжого місяця завжди занижена, і будь-яка модель бачить у кінці ряду
обвал, якого немає. Наскільки занижена — програма міряє сама, відтворюючи
знімки: для кожної закупівлі відомо, коли саме кожна гривня стала видимою, тож
видно й те, як виглядав би ряд тиждень чи місяць тому. На вибірці
березень-серпень 2026 крива розвитку така: у день оприлюднення видно 23%
грошей закупівлі, через тиждень — 55%, через два — 93%, через три — 99%, і
лише на 25-й день ряд закривається. Серпень через це був видний на 79% —
7,1 млн замість 9,1 млн, які там будуть.

Друга поправка — на дні: збір за «останні пів року» починається й
закінчується посеред місяця. Частка місяця рахується не днями, а виміряним
розподілом публікацій за днями тижня: вихідні на цьому ринку майже порожні
(субота 1,2%, неділя 0,7% проти 17-22% у будні), тож обрив у понеділок і обрив
у неділю з'їдають зовсім різну частину місяця.

Обидві поправки показані окремою таблицею з усіма множниками, а місяць, від
якого лишилося менше 40%, у підгонку взагалі не береться: домножити
спостережене більш ніж удвічі — це вже не корекція. Поріг не з голови: зріз на
10 червня бачив червень на 18%, і поправка дала б 28,7 млн замість справжніх
12,3 — помилку в +133%.

**Поправка перевіряє сама себе, і перевірка лежить у звіті.** Для кожного вже
дозрілого місяця програма вдає, що збір урвався його останнім днем, будує криву
лише з того, що було видно тоді, і звіряє скориговане число з тим, що в місяці
опинилося насправді. На вибірці березень-серпень 2026 (п'ять придатних місяців)
середня похибка без поправки — 22% **і завжди в мінус**: місяць недорахований.
З поправкою — 5%, у обидва боки. Таблиця показує кожен місяць окремо, тож число
можна не брати на віру.

Через це прогноз відходить не від видимої частини останнього місяця, а від
оцінки повного: на серпні 2026 це 9,06 млн замість 7,13. На графіку скоригований
ряд іде суцільною лінією через усю історію — з фактом він збігається всюди, крім
неповних місяців, і саме від нього починається прогноз.

**Модель не задана наперед — її обирає перевірка.** Програма перебирає до
п'ятнадцяти моделей: наївну, сталу за медіаною, дрейф, експоненційне
згладжування, метод Тета, стійку пряму Тейла — Сена, Гольта із загасаючим
трендом, їхні варіанти на логарифмах (стала швидкість замість сталого
приросту), сезонну наївну, сезонну поправку поверх згладжування й Гольта та
комбінацію простих. Кожна знає, скільки точок їй потрібно, тож на пів року
сезонні моделі не вмикаються взагалі, а на трьох роках вмикаються самі.

Міряються вони ковзним початком і показником MASE (похибка, поділена на
похибку наївного прогнозу: менше за одиницю — краще за «буде як минулого
місяця»). **Усі моделі перевіряються на однакових згортках** — це та тиха
помилка, через яку згладжування спершу показувало MASE 0,48 проти 1,26 у
наївної, а на спільних згортках — 0,48 проти 1,07: модель, яка почала пізніше,
міряється на коротшому й легшому хвості ряду.

Переможець обирається не чистим мінімумом, а правилом однієї стандартної
похибки: серед моделей, що вкладаються в межу «найкраща + SE», перемагає та,
що приймає найменше рішень. На шести точках різниця в MASE — здебільшого шум,
і складніша модель виграє її випадково. Модель, гірша за наївну, не перемагає
ніколи, навіть якщо вона найощадливіша.

**Межі — не прикраса.** Інтервал 80% рахується за формулами дисперсії ETS із
квантилем Стьюдента (на чотирьох ступенях свободи він на чверть ширший за
нормальний), а якщо ковзна перевірка показала більший розкид, ніж залишки
всередині вибірки, береться її. До цього додається ще одне джерело
невизначеності, про яке зазвичай забувають: **сам вибір моделі**. Формула
дисперсії вважає модель відомою наперед, хоча її щойно обрали тими самими
даними. Перевірено на 120 ковзних прогнозах у п'яти сценаріях: без цієї
поправки 80% межі накривали факт лише в 70-72% випадків, з нею — у 75-80%.
Коли всі рівноправні моделі кажуть те саме, межі не змінюються; коли
сперечаються — розширюються рівно на стільки, наскільки непевний вибір. На пів року історії це дає інтервал ширший за
саме число — і так і має бути: місячний обсяг цього ринку коливається вдвічі,
і робити вигляд, що його можна назвати з точністю до відсотка, було б обманом.

Кожен прогноз підписаний тим, наскільки він перевірений: «перевірено»,
«перевірено побіжно» (менше шести звірок із фактом) або «не краща за наївну».
Таблиця перевірки показує всі моделі з їхнім MASE — видно не лише що обрано, а
й що програло.

Чого прогноз не вміє й не вдає: сезонність без двох повних років, структурні
зміни (нові Особливості, бюджетний рік, вихід великого гравця) і будь-що поза
самим рядом.

### 4. Відмови: чому перемоги не стають договорами

Виграти закупівлю ще не означає підписати договір. Замовник може відхилити вже
визначеного переможця — і, за законом, зобов'язаний назвати підставу. Ця
підстава лежить у самій картці закупівлі, тобто **не коштує жодного зайвого
запиту**: вона приходить разом із карткою, яку програма й так завантажує.

Вкладка показує, як часто це трапляється, з ким і чому:

* скільки рішень про переможця скасовано, яка це частка від усіх ухвалених
  рішень і на яку суму;
* **причини за категоріями** — відмова від договору, невідповідність технічним
  вимогам, ненадані документи, непідписаний договір, недостовірна інформація,
  ненадане забезпечення й решта підстав пункту 44 Особливостей;
* хто саме втрачає перемоги: таблиця компаній із часткою зривів («11 виграшів
  із 13 зірвалися» — це вже характеристика гравця, а не випадковість);
* які замовники відхиляють найчастіше;
* повний перелік випадків із дослівним формулюванням замовника — щоб
  прочитати саме той абзац, яким відхилили вас.

Категорія визначається за формулюванням: замовник переписує підставу з закону,
часто дослівно, тож горстки шаблонів вистачає. Перевірено двічі — на 72
відхиленнях ІТ-вибірки й окремо на **2 000 випадкових закупівлях усієї країни**
(усі галузі, 64 відхилення, класифікатор цих текстів не бачив). Розпізналися
**всі 136**, і розподіл на другій вибірці вийшов геть інший — 29,7%
непідписаних договорів проти 62,5% відмов на ІТ, — тобто шаблони тримаються на
мові закону, а не підігнані під один ринок. Формулювання, яке не впізналося,
потрапляє в «Іншу причину», а не приписується найближчій за змістом.

Окремо видно, **об який документ спіткнулися**: чи згадано у формулюванні
сертифікат, авторизаційний лист виробника, ліцензію, гарантію. Для ринку
ІТ-техніки це часто важливіше за саму категорію.

Другий блок вкладки — **відмінені закупівлі**: там перемогу забирає не рішення
про учасника, а зникнення самої закупівлі. Підстава тут із переліку
(«відсутня потреба», «неможливо усунути порушення законодавства», «обставини
непереборної сили», «скорочено видатки»), тож розпізнавати нічого не треба.

Сума в цьому розділі — **сума скасованих рішень, а не грошей, що зникли з
ринку**: в одній закупівлі замовник відхиляє переможців поспіль (у ІТ-вибірці
так сталося в 15 закупівлях із 46), договір урешті підписує наступний учасник, а
закупівля входить у суму кілька разів. Тому поруч стоїть «Закупівель зачепило»,
і блок про це прямо попереджає.

Одна тонкість, від якої залежить усе число: **скасоване рішення — це не окрема
відмова**. Замовник спершу скасовує власне рішення про переможця й аж потім
оприлюднює відхилення, тож у даних одна подія лежить двома рядками. Виміряно:
51 із 55 скасованих рішень мають таку пару. Програма рахує лише відхилення —
інакше кількість відмов була б завищена на три чверті.

### 5. Наші ТОВ і конкуренти

Для кожного гравця складається портрет: місце в рейтингу, сума й частка,
результативність на торгах, середня та медіанна угода, основна ТМ і основний
товар, цінова поведінка, географія, замовники, повторні звернення, динаміка,
сертифікати й авторизаційні листи в поданих файлах. Поруч — коротка
характеристика звичайною мовою: «монобрендовий гравець», «працює переважно поза
торгами», «агресивна ціна», «географічно сфокусований».

Окремо рахується, **чому конкретна закупівля пішла не до нас**. Відповідей три,
і вони означають різні проблеми:

| Що сталося | Про що це |
|---|---|
| ми не подавалися | моніторинг закупівель |
| програли за ціною | ціна й закупівельні умови |
| нас відхилили — із названою підставою | те, що замовник прямо назвав: техвимоги, документи, строк |
| наша ціна була нижчою, а підстави не названо | якість підготовки пропозиції |

Плюс охоплення ринку: скільки закупівель відбулося в галузях, де ми взагалі
присутні, у скількох ми брали участь і що саме пройшло повз.

### 6. Товари й торгові марки

ТМ визначається за текстом позицій і назвою предмета закупівлі за довідником
[`data/brands.json`](data/brands.json): понад сотня марок ІТ-ринку з
написаннями кирилицею й назвами модельних рядів (`ThinkPad` → Lenovo,
`LaserJet` → HP). Довідник **редагується** — додайте свої марки, і наступний
аналіз рахуватиме їх нарівні з рештою.

Латинські слова з описів, яких у довіднику немає, потрапляють у таблицю
«Кандидати в ТМ» — так довідник не старіє.

**Однакові товари зводяться в один рядок.** Ту саму річ замовники називають
десятком способів — «Миші», «Мишка», «Миша», «Миша дротова», «Комп'ютерне
обладнання (миша)», — і таблиця товарів розсипалася на сотні рядків по одній
позиції. На річній вибірці ІТ-техніки це 397 різних формулювань, з яких 248
(62%) траплялися рівно раз. Після об'єднання лишається **80 товарів**, і 97%
позицій розпізнає довідник [`data/product_types.json`](data/product_types.json),
решту — морфологічне правило.

Розбіжності бувають трьох різних природ, і кожна лікується окремо:

| Природа | Приклад | Ліки |
|---|---|---|
| текст | `Комп'ютер` і `Комп’ютер` — різні символи апострофа | нормалізація |
| морфологія | `Монітор` / `Монітори` | шаблони-основи, а для незнайомого — перший іменник з відрізаним закінченням |
| синоніми | `БФП` = `Багатофункціональний пристрій`, `мишка` = `миша` | лише довідник |

Довідник **редагується**, як і довідник ТМ. Вирішує не порядок рядків, а
**позиція збігу в описі**: українською головне слово стоїть першим, а далі йде
уточнення, тому «кабель для монітора» — це кабель, «кулер для процесора» —
кулер, «килимок для мишки» — килимок. Винятки з цього правила описані явно
полем `beats`: «Накопичувач SSD USB Type-C» починається зі слова «накопичувач»,
але це SSD.

Окремо знімається код ДК021 із назвою класу: кожна п'ята позиція записана як
«30230000-0 Комп'ютерне обладнання (монітор)», де товар названий аж у дужках.

**Таблиць дві, і вони не замінюють одна одну.** «Товари ринку (об'єднані)»
відповідає, скільки насправді купують мишей, і має колонку «Варіанти назви» —
перелік формулювань, які злилися в цей рядок. «Товари ринку (як у документах)»
лишає кожне формулювання окремим рядком: нею перевіряють саме об'єднання й
дивляться, як замовник назвав предмет. Сума позицій в обох однакова — це
закріплено тестом, бо об'єднання не має нічого губити дорогою.

### 7. Канали постачання

Постачальника чи дистриб'ютора у відкритих даних закупівель не публікують.
Тому аналіз збирає сигнали, які там **таки** є:

* ексклюзивність ТМ — марка, з якою у вибірці не заходить більше ніхто;
* власні ТМ із довідника;
* авторизаційні листи виробника та сертифікати — розпізнаються за назвами
  файлів у реєстрі документів;
* постачальник картки товару в е-каталозі;
* хто ще возить ту саму марку.

Там, де з цього висновку не складається, у звіті стоїть чесне
**«Потрібний глибший ШІ аналіз»**, а не вигаданий ланцюжок. Відомі вам зв'язки
«ТМ → дистриб'ютор» вносяться в той самий `brands.json`.

### 8. Порівняння з конкурентами

Сильні та слабкі сторони виводяться з вимірюваних ознак: кількість різних ТМ,
монобрендовість, сертифікати й авторизації, дисконт проти ринкового,
результативність, географія, стійкість бази замовників, динаміка.

На графіках цього розділу компанія рахується двома різними числами, і плутати
їх не варто: **ТМ у портфелі** — усе, з чим гравець виходив на торги, а
**проданих ТМ** — лише марки з виграних закупівель. У того, хто багато
подається й мало виграє, різниця помітна.

Наші ЄДРПОУ виділені кольором на кожному графіку компаній і показані завжди.
Якщо наше ТОВ не ввійшло у видиму верхівку рейтингу, воно дописується в кінець
списку з номером свого справжнього місця — «НАШЕ ТОВ (№21)». Раніше воно за
межею топ-15 просто зникало з графіка.

Чого з цифр не видно взагалі — власне виробництво й локалізація, умови
дистрибуції та кредитні ліміти, глибина складу, сервісна мережа, якість
передпродажної підтримки — звіт називає прямо й позначає тим самим
«Потрібний глибший ШІ аналіз».

Увесь звіт зберігається в Excel кнопкою внизу сторінки — і зберігається таким,
яким він на екрані. Аркуш повторює вкладку: спершу показники, потім висновки,
потім графіки, потім таблиці. **Кожна діаграма стоїть праворуч від власних
даних**: ліворуч табличка, з якої вона намальована, праворуч — сама діаграма,
тож будь-який стовпчик можна перевірити очима. Діаграми справжні, а не
картинки: вони живуть на своїх клітинках, і в книзі їх можна крутити,
перефарбовувати й тягнути в презентацію. Кольори ті самі, що на екрані, наші
ТОВ виділені так само.

Другий аркуш книги — **«Графіки»**: усі діаграми звіту зібрані в одному місці,
по дві в ряд, згруповані за розділами. Розділів дев'ять, і щоб побачити картину
цілком, доводилося клацати по вкладках, тримаючи попередню в голові. Даних цей
аркуш не дублює: кожна діаграма читає ті самі клітинки на своєму рідному
аркуші, тож книга від нього майже не важчає (виміряно: 608 → 635 КБ на 32
діаграми), а числа лишаються в одному місці. Під назвою кожного розділу
підписано, на якому аркуші шукати дані. Графік, який стоїть і в «Підсумку», і у
своєму розділі, показано один раз; портрети окремих компаній сюди не входять —
у них 137 діаграм на 39 аркушах, і аркуш перетворився б на другу книгу.

Портрет кожного гравця — окремий аркуш зі своїми діаграмами, таблицями,
сильними й слабкими сторонами; перший аркуш «Зміст» перелічує все з
посиланнями. Таблиці оформлені «розумними таблицями» Excel, тож у кожної свій
фільтр і своє сортування.

**Звіт по одній компанії.** На сторінці будь-якого гравця — нашого ТОВ чи
конкурента — є кнопка «Зберегти звіт по компанії»: книга з одного аркуша, у
якій рівно те, що показує ця сторінка, — показники, висновки, сильні та слабкі
сторони, таблиці й діаграми праворуч від своїх даних. Під назвою компанії
підписано, з якого вивантаження й за який період узяті дані, тож книгу можна
віддати як є. Важить вона десятки кілобайт і пишеться за частку секунди —
зручно, коли треба показати одного конкурента, а не весь ринок.

Розмір повної книги залежить від вибірки: звіт на 40 556 закупівель — це
45 аркушів, 199 таблиць (49 687 рядків) і 231 діаграма, 3,8 МБ, запис 10-12 с;
звіт по одній компанії з тієї самої вибірки — 68 КБ і 0,2 с.

## Файли закупівель

Качається все, що є в картці: тендерна документація, документи пропозицій
учасників, протоколи кваліфікації, договори та додатки, скарги й скасування.
Пошук документів рекурсивний по всьому JSON — навіть якщо Prozorro додасть новий
розділ, файли з нього все одно потраплять у вивантаження.

```
downloads/
├── prozorro-дані-2026-08-17-2002.xlsx    ← таблиця з даними
└── 2026-08/
    └── UA-2026-08-13-007779-a Моноблоки…/
        ├── UA-2026-08-13-007779-a.json    ← повна картка закупівлі
        ├── Закупівля/                     ← тендерна документація
        ├── Пропозиція/
        │   └── 12345678 ТОВ «Постачальник»/
        ├── Кваліфікація/
        └── Договір/
```

Відокремлені підписи КЕП (`.p7s`) типово пропускаються: змісту в них немає, а
на перевіреному зрізі це **468 файлів із 1 591 — 29% штук і 205 МБ із 1,1 ГБ**.
Поруч є поле «лише ці типи файлів» із заготовками «PDF і Word» та «Документи
й архіви». Архіви навмисно входять у другу заготовку: учасники часто вантажать
усю пропозицію одним zip чи rar, і без них губиться змістовна частина
(на тому ж зрізі — 70 файлів і 210 МБ).

Відсіяне не зникає: у таблиці «Файли» такі документи мають стан «Відсіяно
фільтром» із причиною. Змініть фільтр і натисніть «Завантажити відсутні» — вони
завантажаться, переробляти нічого не треба.

Сервер документів під навантаженням рве з'єднання посеред передавання, тож
кожен файл перечитується цілком до трьох разів, а недовантажений файл ніколи не
потрапляє на диск під справжньою назвою: спершу пишеться `.part`, і лише повний
файл перейменовується.

## База: знімок одного збору, а не архів

Типово **зібране очищається перед кожним новим збором** («Налаштування» →
«Збереження файлів»). Без цього база стає архівом усіх колишніх пошуків, і
аналітика рахує ринок по суміші вибірок: свіжі ІТ-закупівлі разом із залишками
попереднього збору за іншим класом ДК021. Одна вибірка — один збір.

Індекс `tenderID → UUID` і покриття стрічки змін очищення **не зачіпає**: вони
здобуваються годинами обходу й до предмета збору стосунку не мають. Прибрати
зібране, не запускаючи новий збір, можна кнопкою «Прибрати зібране» там само.

У режимі «тільки дані» **посилання на файли не зберігаються**: у типовій
закупівлі це два десятки підписаних адрес по двісті символів, і на сорока
тисячах закупівель вони важать більше за всі картки разом (на реальній базі —
107 МБ із 532). Назва, тип, розділ і власник файлу лишаються завжди — саме за
ними аналітика впізнає сертифікати й авторизаційні листи. Якщо файли таки
знадобляться, їх дає кнопка «Зібрати файли»; «Завантажити відсутні» в такому
разі чесно скаже, що адрес немає.

Усе, що програма створює, — всередині теки проєкту. Її можна перенести чи

| Що | Де |
|---|---|
| Таблиці й файли закупівель | `downloads\` |

## Що з потрібних даних реально є у відкритих джерелах

Програма збирає з двох джерел: картки закупівель (ЦБД) і картки товарів
е-каталогу Prozorro Market. Перевірено на вибірці з 40 карток каталогу.

## Фільтри пошуку

* **Період** за датою оприлюднення, з готовими пресетами: 12/6/3 місяці,
  поточний і минулий рік. Переставлені межі виправляються самі.
* **Дерево ДК021:2015** з пошуком за кодом і назвою; позначений вузол означає
  «цей код і все, що під ним». Швидкі набори: ІТ-техніка, комп'ютери й ноутбуки,
  монітори, оргтехніка, ПЗ, телеком.
* **ЄДРПОУ конкурентів** — знаходить усі закупівлі, де вони подавали пропозицію
  або перемагали. Так само для замовників. Можна вставити кілька кодів одразу.
* **Уточнення**: статус, тип процедури, регіон замовника, діапазон очікуваної
  вартості.
* **Картки товарів е-каталогу** — окремий прапорець; єдине джерело технічних
  характеристик, фото й цінових діапазонів.

Решта сторінок: **Результати** — таблиця з фільтром і сортуванням;
**Файли** — реєстр документів зі станом кожного; **Журнал** — перебіг роботи
й помилки; **Налаштування** — тека збереження, ЄДРПОУ ваших ТОВ і конкурентів,
темп запитів, обмеження на розмір файлів, тема, керування індексом.

## Як це працює: два джерела даних

Програма поєднує два відкриті API, бо жоден із них поодинці не дає всього.

**1. Пошук порталу** — `POST https://prozorro.gov.ua/api/search/{tenders,contracts,products}`

Уміє фільтрувати за `cpv`, `tenderer` (ЄДРПОУ учасника), `buyer`, `supplier`,
`status`, `proc_type`, `text`. Особливості, які довелося врахувати:

* коди ДК021 шукаються **точним збігом**, ієрархії немає — але кілька кодів в
  одному запиті об'єднуються через **АБО**, тож увесь набір іде одним запитом,
  а не запитом на кожен код (перевірено на живому API);
* сторінка — 20 записів, максимум 500 сторінок (10 000 записів) на запит,
  і збільшити сторінку не можна (`per_page`, `limit`, `size` ігноруються);
* **фільтра за датою немає** (перевірено десяток імовірних назв параметрів —
  усі ігноруються), зате результати відсортовані від найновіших, тому гортання
  зупиняється, щойно доходимо до початку періоду;
* **упорядкування й відбір спираються на одну дату.** Видача відсортована за
  датою оприлюднення (вона ж у номері `UA-2026-08-06-…`), і саме їй дорівнює
  `dateCreated` у Центральній базі, за яким закупівля відбирається в період —
  збіг перевірено на живих даних. Колись відбір ішов за початком подання
  пропозицій, тобто за іншою датою, і доводилося гортати на 30 днів глибше;
  тепер запас `LOOKBACK_SLACK_DAYS` — дві доби, суто на межу часових поясів;
* у відповіді немає внутрішнього ідентифікатора закупівлі.

### Стеля видачі: чому пошук іноді треба ділити

Стеля в 10 000 записів спільна для всього запиту, тож на довгому періоді один
запит просто не дістає до його початку. Ділити період неможливо — фільтра за
датою немає, — тож ділиться сам запит:

1. **за кодами ДК021** — набір розрізається навпіл. Найдешевше й завжди коректно;
2. **за типом процедури** (`proc_type`), коли код лишився один. Кожна закупівля
   має рівно один тип, тож розріз не дає ані перетинів, ані втрат (перевірено:
   сума за процедурами збіглася із загальною), а глибина зростає з місяців до
   років — стеля рахується для кожного запиту окремо. Одне значення,
   `closeFrameworkAgreementSelectionUA`, довше за дозволені 30 символів і тому
   пошуком недоступне — такі закупівлі добираються зі стрічки змін (нижче);
3. **за замовником**, коли й код, і процедура вже одні. Стеля стоїть не на
   кількості записів, а на адресації — сторінки за 500-ту просто немає
   (`The page may not be greater than 500`), тож «взяти двома заходами по
   7 500» не вийде: другий захід уперся б у ту саму сторінку. Дістатися
   глибших записів можна лише запитом, у якому вони опиняться в перших
   10 000. Замовник для цього годиться: у кожної закупівлі він рівно один,
   а список ЄДРПОУ пошук об'єднує через АБО і приймає щонайменше 20 000
   значень за раз. Перелік замовників береться з карток, які й так
   перегорнуто (пошук віддає `procuringEntity` у кожному записі), тож розріз
   не коштує жодного зайвого запиту — лише повторного гортання.

Розріз за замовником **не гарантує повноти**: замовника, якого не було видно в
межах перших 10 000, у ньому не буде. Зате він показує те, чого раніше не було
видно взагалі, — справжній розмір запиту: сервер обрізає `total` рівно на
10 000, а сума по групах каже, скільки записів насправді.

Далі розрізати нема чим: `region` пошук відхиляє з будь-яким значенням,
`per_page` й `sort` ігнорує, а `status` хоч і ділить видачу, та вкрай нерівно
(на `reporting` виміряно 7 880 = 7 622 `complete` + 83 `cancelled` + 0
`unsuccessful`). Тому коли не лишилося й замовників, програма каже прямо, **до
якої дати запит дістає**: «дістає лише до 2026-03-14, а період починається
2025-08-28». Зарадити тут може лише пізніша дата «з» або вужчий перелік кодів —
**ранішня дата «по» не допомагає**: видача завжди починається від сьогодні, і
стеля витрачається на найновіші записи, які потім відкидаються як «поза
періодом».

### «Відбір за рамковою угодою»: те, чого пошук не вміє

`closeFrameworkAgreementSelectionUA` — 34 символи, а сервер відхиляє
`proc_type` довший за 30 (`The proc_type.0 may not be greater than 30
characters`). Зате цей тип віддає стрічка змін ЦБД, з якої будується локальний
індекс, тож він пишеться в індекс поруч із номером і UUID. Після пошуку
програма добирає такі закупівлі просто з індексу, а далі вони проходять ті самі
фільтри, що й решта (ДК021, дата, регіон) — коди ДК021 стрічка не віддає, тому
перевіряти їх доводиться вже за повними картками.

У стрічці таких закупівель 0,05% (виміряно на 6 000 записів) — сотні на рік,
тобто хвилина довантаження. За кількістю це справді одиниці, а от за грошима —
ні: у річній вибірці по ДК021 3021* їх було 7 на 29,9 млн грн, із середньою
угодою 4,3 млн — найбільшою на ринку. Індекс, зібраний до появи цієї
можливості, типу процедури не має: програма про це попереджає й радить
перебудувати індекс за період.

**Глибина з'ясовується двома запитами, а не гортанням.** Сторінки адресуються
номером, тож досить спитати останню доступну й подивитися її дату: якщо вона
все ще новіша за початок періоду, запит треба ділити. Тому пошук спершу
складає план (на річному періоді це ~30 запитів за кілька секунд і 18 запитів
у плані), і лише потім гортає — маючи наперед відому кількість сторінок, а
отже й чесний відсоток на смузі.

Раніше глибина з'ясовувалася аж після 500 сторінок гортання: кожна невдала
спроба коштувала ~8 хвилин квоти, після чого набір ділився й половини гортали
те саме наново. На річному періоді це давало години марної роботи.

**Квота: 60 запитів на 60 секунд.** Виміряно на живому сервері: рівно 60
успішних запитів поспіль, 61-й — `429` із `Retry-After`, що дорівнює 60 секундам
мінус час від першого запиту. Портал рахує не миттєвий темп, а кількість запитів
у вікні, тож будь-який сталий темп понад один запит на секунду вичерпує бюджет
достроково, після чого сервер мовчить до кінця вікна. Заголовки (`User-Agent`
браузера, `Referer`, `Origin`) на це не впливають — перевірено окремо.

`WindowLimiter` у [`app/core/http.py`](app/core/http.py) тримає позначки часу
зроблених запитів і чекає рівно доти, доки найстаріша не вийде за межі вікна.
Короткий пошук завдяки цьому проходить на повній швидкості, довгий — рівно на
межі квоти, і 429 не виникає взагалі.

**Хости зіставляються точно за іменем, а не за підрядком.** Це не дрібниця:
`market-api.prozorro.gov.ua` містить `prozorro.gov.ua` як підрядок, але має
**власну** квоту — перевірено, що поки портал відповідає 429, каталог віддає
картки без жодної відмови, близько 24 запитів/с. Через зіставлення за підрядком
збір карток товарів даремно сидів на квоті порталу: клас із 2 400 карток
читався 41 хвилину замість двох.

| Сервер | Межа | Звідки число |
|---|---|---|
| `prozorro.gov.ua` | 58 запитів на 60 с | виміряно: 60-й проходить, 61-й — 429 |
| `market-api.prozorro.gov.ua` | 20 запитів/с | виміряно 23–24 на 4–8 з'єднаннях |
| `public.api.openprocurement.org` | 28 запитів/с | виміряно 29–34 на 16 з'єднаннях |
| решта | «Темп для інших серверів» у налаштуваннях | — |

Числа для другого й третього — це **оцінка, а не обіцянка сервера**, тож темп
підлаштовується: на 429 знижується, за серії вдалих запитів повертається до
виміряного. Для таких хостів реакція навмисно м'яка (крок 1.25, повернення
після десяти вдалих): різке відступання, доречне там, де межа невідома,
просідало цілий етап на п'яту частину часу через одну випадкову відмову на дві
тисячі запитів.

### Скільки це триває насправді

Заміряно на класі `3021` (25 кодів), лише дані, без файлів і каталогу:

| Період | Знайдено | Час | Запитів до порталу |
|---|---|---|---|
| 7 діб | 504 | ~40 с | 31 |
| 30 діб | 1 791 | ~3,5 хв | 122 |
| 365 діб | ~58 000 | ~1,5–2 год | ~3 380 |

Пошук упирається у квоту порталу і йде на її межі: на місячному періоді
122 запити при теоретичному мінімумі 90 (1 791 запис по 20 на сторінку) —
тобто в межах 7% від межі можливого. Решта часу — Центральна база, яка квоти
не має. Розпізнавання й читання карток ідуть у три-чотири рази швидше за
пошук, тож саме довжина періоду й визначає час.

**2. Центральна база даних** — `https://public.api.openprocurement.org/api/2.5`

Офіційний відкритий API з повними картками: лоти, номенклатура з кодами ДК021,
пропозиції учасників, кваліфікації, договори і прямі посилання на файли.
Адресує закупівлі внутрішнім UUID.

**3. Е-каталог Prozorro Market** — `https://market-api.prozorro.gov.ua/api/products/{id}`
([документація](https://market-api.prozorro.gov.ua/api/doc))

Картки товарів: бренд і модель у назві, штрихкод EAN, опис, категорія, фото
та структуровані технічні характеристики з одиницями виміру. Каталог
класифікує товари на рівні класу ДК021 (`30210000-4`), тому обрані коди
підіймаються до свого класу. Назву категорії картка тримає кодом
(`relatedCategory`), тож вона розкривається запитом до `/api/categories/{id}`;
відповіді кешуються, бо на сотні товарів припадає кілька категорій.

Раніше картки читалися з `prozorro.gov.ua/api/products/{id}` — це
недокументований проксі порталу над тим самим каталогом, який до того ж
збіднював відповідь (губив код одиниці виміру та класифікацію характеристики
за ESPD211). Показово, що сам проксі у полі `url` повертав саме адресу
`market-api`, і фото віддавав з цього ж хоста.

**Чому пошук лишився на порталі.** Відбору за ДК021 в `market-api` немає:
`GET /api/products` віддає лише хронологічну стрічку змін (`{id, dateModified}`,
сторонні фільтри мовчки ігноруються), а `POST /api/search` — це добір за
готовим переліком `id`, та й той закритий для анонімних клієнтів. Тому картки
**відбираємо** пошуком порталу, а **читаємо** з `market-api`.

**Частину карток каталог не віддає — і це нормально.** На товар, чия категорія
вилучена з довідника, `market-api` відповідає `404 {"errors": ["Category not
found"]}`. Це стан його власних даних, а не збій зв'язку: перевірено 01.09.2026
на ідентифікаторах із **власної стрічки каталогу** — усі вісім найдавніших
(2023 рік) дали 404, усі вісім найновіших — 200. Пошук порталу такі картки
все одно показує, і навіть зі статусом `active`. Запасного джерела немає:
недокументований проксі порталу, який колись віддавав ті самі картки, тепер
відповідає 503.

Тому програма не сипле рядком на кожну таку картку, а рахує їх і пише один
підсумок: скільки не віддалося, який це відсоток вибірки й чому. Справжні збої
(500, розрив зв'язку) лишаються видимими поштучно — але не більше п'яти, щоб
журнал не перетворювався на тисячу однакових рядків.

### Місток між джерелами: локальний індекс

Пошук дає номер `UA-2026-08-13-007779-a`, а файли лежать за UUID. Способів два,
і вони мають протилежну вартість:

| Спосіб | Чого коштує | Коли вигідний |
|---|---|---|
| **Опитати портал поштучно** — `GET /api/tenders/{номер}/summary` | один запит на закупівлю з квоти порталу (58 на хвилину) | вузькі вибірки: пошук за одним ЄДРПОУ, кілька десятків закупівель |
| **Локальний індекс** — обхід стрічки змін ЦБД | пропорційно **довжині періоду**, а не розміру вибірки; квоти не витрачає зовсім | усе інше: сотні й тисячі закупівель |
| **Автоматично** (типово) | обирає дешевше: приблизно півтори закупівлі на добу періоду — межа, де індекс починає вигравати | завжди |

Обидва дають стовідсоткове покриття. Раніше був і третій шлях — через пошук
договорів, — але заміри показали, що він витіснений обома: на вибірці з 504
закупівель разом з індексом він дав ті самі 477 за 80 секунд і 19 запитів до
порталу, тоді як сам лише індекс дав ті самі 477 за 13 секунд і **без жодного
запиту до порталу**. До того ж він знаходив тільки ті закупівлі, за якими
договір уже укладено. Шлях вилучено.

Побудова індексу — це прохід стрічки `dateModified` Центральної бази: близько
**8 500 записів/с**, за добу в стрічці ~13 тисяч записів. Період ріжеться на
відрізки за кількістю потоків (типово вісім) — саме в цьому й пришвидшення:
стрічка гортається курсором, тож усередині відрізка паралелізму немає. Раніше
різали строго помісячно, і на короткому періоді виходив один відрізок — вісім
діб стрічки гортались одним потоком. Пройдені доби не обробляються вдруге, тож
побудову можна зупинити й продовжити, а наступні запуски лише дописують нове.

## Обмеження, про які варто знати

* **Пошуковий портал має квоту 60 запитів на 60 секунд** — не темп, а бюджет
  на вікно (`/api/search`, `/api/tenders/…/summary`). Це найдефіцитніший ресурс
  програми, тож усе, що можна, зроблено в Центральній базі, яка квоти не має.
  Саме довжина періоду й визначає час збору: пошук іде на межі квоти, а решта
  етапів у три-чотири рази швидша.
* **Квота стосується лише самого порталу.** `market-api.prozorro.gov.ua` має
  власну — перевірено, що поки портал відповідає 429, каталог віддає картки без
  жодної відмови. Тому клас ДК021 на 2 400 карток читається дві хвилини, а не
  сорок. Каталог не має періоду: картка описує поточний стан пропозиції, тому
  фільтр за місяцями на нього не діє, а прапорець «лише чинні картки» скорочує
  обсяг приблизно на третину.
* **Стеля видачі — 10 000 записів на запит.** На довгому періоді один запит до
  її початку не дістає, тож програма ділить сам запит: спершу за кодами ДК021,
  далі за типом процедури. Глибина з'ясовується двома запитами наперед (див.
  «Стеля видачі» вище), тож марного гортання не буває. Коли ділити більше нема
  чим, програма називає дату, до якої запит дістає — зсунути вікно в минуле
  пошук не дозволяє. Процедуру `closeFrameworkAgreementSelectionUA` (назва
  довша за дозволені 30 символів) програма добирає зі стрічки змін ЦБД.
* **Причина відхилення переможця — вільний текст**, а не код. Програма
  зводить формулювання до категорій за шаблонами; те, що не впізналося,
  лишається «Іншою причиною» й не приписується найближчій за змістом.
  Підстава відміни всієї закупівлі, навпаки, приходить переліком.
* **Скасоване рішення про переможця — не окрема відмова**: замовник спершу
  скасовує власне рішення, а вже потім оприлюднює відхилення, тож одна
  подія лежить у даних двома рядками (виміряно: 51 із 55 скасованих мають
  таку пару). Рахуються лише відхилення.
* Постачальник у картці вказаний у рішенні про переможця, а не в самому
  договорі: `contracts[].suppliers` там майже завжди порожній. Програма
  підставляє його за `awardID` — без цього вся аналітика «хто продав»
  лишалася б без кодів ЄДРПОУ.
* **Очікувана вартість і сума договору можуть бути в різних базах ПДВ.**
  Приблизно в половині закупівель очікувану вартість вказано без ПДВ, а договір
  укладено з ним — тоді сума договору рівно на 20% більша. Через це підсумок
  «сума договорів» іноді перевищує «очікувану вартість», і це не помилка.
  Ознака є в колонці «ПДВ включено» на аркуші «Закупівлі».
* Фільтр за регіоном бере адресу замовника. Близько десятої частини замовників
  її не заповнює — такі закупівлі до вибірки за регіоном не потраплять.
* Дати — за оприлюдненням закупівлі, а не за підписанням договору.
* Конфіденційні документи в Prozorro не мають публічного посилання, тож
  завантажені бути не можуть — вони просто не потрапляють у перелік.
* Звіти про укладений договір (`reporting`) — це не тендери, а повідомлення про
  пряму закупівлю. У них зазвичай немає жодного документа, крім підпису, тож
  тека такої закупівлі виглядає порожньою. Це дані джерела, не збій.

## Перевірено на реальних даних

Клас `3021` (25 кодів) за 30 діб, режим «тільки дані»: знайдено 1 791,
розпізнано **1 791 з 1 791**, завантажено 1 791 картку — 648 лотів, 2 130
позицій, 25 389 документів за **3,5 хвилини**, нуль помилок і попереджень.
Перевірка бази після прогону: жодного запису поза періодом, жодного з чужим
кодом ДК021, жодного дубліката, жодного без назви чи ЄДРПОУ замовника.

Пошук при цьому зробив 122 запити до порталу при теоретичному мінімумі 90
(1 791 запис по 20 на сторінку) — тобто **в межах 7% від межі можливого**.
Далі прискорити не можна: розмір сторінки й квота задані сервером.

Повний цикл із файлами (ДК021 30232110-8 за 7 діб): 12 закупівель, 43
документи, **31 файл завантажено, 0 збоїв**, 7,6 МБ — усе за 10 секунд.

Розріз за типом процедури перевірено на збіг з еталоном без розрізу: **209
проти 209**, нуль втрат, нуль перетинів між процедурами.

Причини відмов перевірено на 893 картках ІТ-техніки за березень-серпень
2026: із 837 ухвалених рішень про переможця **72 (8,6%) відхилено у 46
закупівлях на 11,3 млн грн**. Підставу названо у всіх 72, пояснення — у 58; розпізналися
всі 72, «Іншої причини» не лишилося жодної. Головні причини — відмова
переможця від договору (45), невідповідність технічним вимогам (15),
непідписаний договір (6). Один гравець вибірки має 11 зірваних перемог
проти 2 виграних — 84,6%.

Класифікатор окремо перевірено на вибірці, якої він не бачив: 2 000 випадкових
закупівель усієї країни за березень-червень 2026 дали 64 відхилення — **усі
розпізнано**, жодної «Іншої причини». Там-таки перевірено інваріанти: жодного
повторного відхилення тієї самої пропозиції, 92% скасованих рішень мають
`unsuccessful`-двійника (проти 93% на ІТ-вибірці), і жодного коду підстави
відміни поза довідником. Ланцюг «збір → база → книга → аналітика» звірено
поаркушно: кількість і сума відмов у базі, у книзі даних, у зведенні та у звіті
збігаються до копійки.

Каталог товарів: клас на 2 405 карток прочитано за **дві хвилини** (2 317
збережено); на вибірці з 22 карток заповнені всі поля — назва, бренд,
категорія, ДК021, штрихкод, опис, фото, — 678 характеристик, з них 262 з
одиницею виміру.

Аналітика на книзі з 4 333 рядків (373 закупівлі, 1 152 позиції, 2 012
документів): **звіт за 0,3 с**, з розрахунків виключено 5 угод і 6 позицій зі
структурним браком і статистичними викидами.

Робочий масштаб — книга на **10 000 закупівель**: 187 760 рядків, 10,8 МБ,
2,3 млн клітинок. Читання **8,6 с**, аналіз **1,0 с**, пам'ять під даними —
59 МБ. Для порівняння, на `openpyxl` і без кешів те саме читалося 37 с,
рахувалося 6,8 с і займало 191 МБ.

Найбільша перевірена вибірка — 40 556 закупівель (книга на 105 МБ): читання
56 с, аналіз 7 с, запис звіту з 231 діаграмою — 10-12 с (звіт по одній
компанії — 0,2 с). Три чверті часу запису — це XML-серіалізація в `openpyxl`,
решта — півмільйона клітинок книги.

Вікно при цьому не завмирає: розбір іде у фоновому потоці (його можна
зупинити), а вкладки й портрети конкурентів збираються тоді, коли їх уперше
відкривають — найважча вкладка будується 0,4 с, портрет конкурента 0,3 с.

Перевірити після змін:

```bash
.venv\Scripts\python -m tests.test_core
.venv\Scripts\python -m pyflakes app tests
```

Виміряні межі API, пастки цього коду й порядок роботи з ним зібрані окремо
в [CLAUDE.md](CLAUDE.md) — там усе, що інакше довелося б з'ясовувати наново.

Залежності — `PySide6-Essentials`, `requests`, `openpyxl`. Саме Essentials, а не
повний `PySide6`: програмі потрібні лише QtCore, QtGui та QtWidgets, а повний
пакет тягне ще й Addons (QtWebEngine, Quick, Charts) — понад 400 МБ, які тут не
використовуються. Саме тому діаграми в аналітиці намальовані вручну: замість
QtCharts — трохи коду в `ui/widgets/charts.py`.

Дані в `data/` — офіційні класифікатори з репозиторію
[ProzorroUKR/standards](https://github.com/ProzorroUKR/standards).

## Що далі

Наступний крок — розбір **вмісту** завантажених документів: витяг назви товару
з торговою маркою, моделі, наявності сертифікатів і гарантійних умов із PDF та
DOCX. Зараз файли зберігаються й реєструються, а аналітика судить про них лише
за назвами — цього досить, щоб побачити сертифікат чи авторизаційний лист, але
замало, щоб дістати з них модель, ціну за одиницю та умови постачання. Саме там,
де тексту не вистачає, звіт і пише «Потрібний глибший ШІ аналіз».

Структура бази до цього готова: у SQLite зберігаються всі лоти, номенклатура з
кодами ДК021, пропозиції кожного учасника з ЄДРПОУ й сумами, переможці,
договори та реєстр документів зі шляхами на диску.
